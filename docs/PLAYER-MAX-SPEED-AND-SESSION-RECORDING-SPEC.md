## 0. Рішення, на яких стоїть специфікація

Дослідження 2026-10-26 (після коміту `72cbcd7`) розглянуло по три варіанти для
кожного питання. Прийнято:

| Питання | Обрано | Відкинуто зараз |
|---|---|---|
| Найшвидше отримання готового малюнка | **Бюджетний планувальник тіків** (варіант 1): ті самі кроки симуляції, але скільки GPU встигає за кадр, а не фіксовані N | Знижена якість кроку (менше PBD-ітерацій); «нанести, потім розтекти» — змінюють вигляд |
| Формат запису мазків | **A — журнал тіків рушія** як основне джерело + **C — опорні точки**, похідні від A | B — сирі pointer events (більші, повтор неточний) |

Чому саме так — коротко:

- Крок симуляції залежить від попереднього (адвекція рідини, PBD ворсинок), тож
  кількість кроків дорівнює кількості семплів мазка. Пропуск кроків змінює
  малюнок. Залишається лише виконувати ті самі кроки щільніше.
- Один крок — це ≈80–100 проходів `Brush.update` (`ITERATIONS = 20`) + 2
  splat + 7 проходів рідини. На 16× це ≈1,5–1,8 тис. draw calls на кадр.
  Стелю задає GPU/драйвер конкретного пристрою, а не множник у select.
- Живий результат визначає не pointer event, а ціль, яку `FluidEngine.advance()`
  отримала на кожен тік 60 Гц. Записувати треба саме її: тоді повтор
  відтворює те, що бачив користувач.

## 1. Частина I — швидкість `Max`

### 1.1. UI

Select `#story-speed` у вкладці **Player** отримує останню опцію під `16×`:

```html
<option value="max">Max</option>
```

| Вимога | Деталі |
|---|---|
| Положення | Остання в списку, одразу після `16×`. Типова опція лишається `8×`. |
| Підпис у select | `Max` |
| Статус під час програвання | `Playing · Max ≈ 23× · 1 380 ticks/s` — фактичний множник і тіки/с, ковзне середнє за 1 с, оновлення не частіше 2 разів/с. До накопичення першої секунди: `Playing · Max (measuring…)`. |
| ETA | Для Max обчислюється з виміряної швидкості (`pending ticks / ticks per s`), а не з `targetPlaySeconds()`. До першого виміру ETA прихований. |
| Зміна під час Playing | Як і для числових швидкостей: safe scheduler hand-off із поточного playhead, без повторного нанесення (`UnpaintedRangeRegistry`). |
| URL | `?storySpeed=max` еквівалентний вибору опції. `storyFramesPerStep` і далі має пріоритет і вимикає fast-forward. |
| Чесність | Max ніколи не показує фіксоване число як обіцянку. Якщо пристрій тягне менше 16×, статус показує, наприклад, `Max ≈ 11×`. |
| Відгук UI | Під час Max кадр екрана не повинен перевищувати ~2× інтервал дисплея довше, ніж на 1 с (див. 1.3): кнопки Pause/Stop і ручний жест мають реагувати так само, як на 16×. |

### 1.2. Контракт контролера

- `StoryPlaybackController.setSpeed(multiplier)` приймає `0.25 | 0.5 | 1 | 2 | 4 | 8 | 16 | 'max'`.
  Інші значення — `RangeError`, як і зараз.
- `this.speed === 'max'` не бере участі в `targetPlaySeconds() / speed`;
  `targetDuration` для Max — `null`, UI відображає виміряний ETA.
- `TilecraftStrokePlayer.play()/playPlan()` отримують замість `ticksPerFrame`
  об'єкт планувальника (`tickScheduler`) з інтерфейсом:
  `beginFrame()`, `shouldContinue() → boolean`, `endFrame()`.
  Числові швидкості реалізуються тим самим інтерфейсом (`FixedTickScheduler(N)`),
  Max — `BudgetTickScheduler`. У player'і лишається одна гілка fast-path.

### 1.3. `BudgetTickScheduler`

Мета: якомога більше тіків за кадр, не замораживши головний потік.

1. **CPU-бюджет.** У межах кадру тіки виконуються, доки
   `performance.now() - frameStart < budgetMs` (типово 10 мс).
2. **Адаптивна стеля `K` (AIMD).** CPU-час не враховує виконання GPU: WebGL
   лише ставить команди в чергу, і переповнена черга з'являється як довгий
   наступний кадр. Тому:
   - інтервал дисплея `D` оцінюється медіаною перших 10 RAF-інтервалів;
   - якщо два кадри поспіль мають RAF-інтервал `> 1.5·D` — `K = max(1, floor(K·0.7))`;
   - інакше `K = min(K + 1, 256)`;
   - стартове `K = 16`, тож Max ніколи не повільніший за 16× на старті.
   За кадр виконується `min(K, тіки, що вмістилися в бюджет)`.
3. **Прихована вкладка.** RAF зупиняється, тож playback теж; при поверненні `D`
   та `K` переоцінюються.
4. **Відмальовка.** Як і зараз, presentation — один раз на кадр
   (`painter.needsRedraw`), незалежно від кількості тіків.

### 1.4. Інваріант «Max без втрат»

Max змінює лише групування тіків за кадрами, а не їхню послідовність.

**INV-MAX-1.** Кожен `advanceTick()` у fast-режимі виконує **рівно один** крок
`simulate()` (`engine.timingStats.steps === 1`), незалежно від того, скільки
реального часу минуло.

Чому це не виконується автоматично: `_advanceStoryTick()` зараз рахує
`storyClock = max(storyClock, wallNow) + 1/60`. Якщо один тік займає більше
16,7 мс реального часу (слабкий GPU, великий прямокутник симуляції),
`advance()` побачить `elapsed > 1/60` і вставить додаткові кроки (до 5) з
інтерпольованою ціллю. Результат тоді залежить від того, як тіки розкладені
по кадрах. Реалізація має прибрати залежність від wall clock для fast-тіків:
наприклад, через публічний примітив `engine.stepTick()` (див. 2.3), який робить
рівно один крок із поточною live-ціллю.

**Наслідок, що перевіряється тестом:** для одного й того самого плану на одному
пристрої `exportPixels()` після `Max` побітово дорівнює результату `16×`.

## 2. Частина II — запис сесії (формати A + C)

### 2.1. Що таке «сесія»

Сесія — послідовність усього, що змінило мокру фарбу з моменту **Record** до
**Stop**:

- тіки рушія під час мазка: ціль `(x, y, height, scale)`, яку отримав `brush.update()`;
- межі мазків: `beginStroke` (колір, розмір, форма пензля, `randomizeBristles`,
  `resolutionScale`, painting rectangle, **варіація натискання**) і `endStroke`;
- нерухомі контакти (`_liveContact(true)`: тап коротший за тік, фінальна точка на `endStroke`);
- холості тіки, коли рідина ще тече після мазка (кодуються довжиною серії);
- команди застосунку: Clear, Undo, Redo, Bake, Natural/Digital, Quality,
  fluidity, bristle count, `paintPathSegment` зі story playback, undo-знімки
  (`snapshot`) і story baseline (`story-baseline` / `story-restore`). Форма
  пензля й кут їдуть у `STROKE_BEGIN` (`brushShape`), окремих команд не треба.
- **Не записуються, а завершують запис** (рішення власника 2026-10-26, фаза 3):
  Resize (commit) і зміна фонового зображення (File, story-сцена). Resize
  перевизначає систему координат painting; записане до нього зберігається.

Не записуються: панорамування, zoom, hover без контакту (beginStroke однаково
переініціалізує ворсинки), рухи UI-панелей.

### 2.2. Рівень захоплення

```text
PointerDispatcher ─► Paint (onGesturePan, _syncBrushToPointer)
                        │ strokeTo() — mailbox, без запису
                        ▼
                   FluidEngine.advance()  ── tick observer ──► SessionRecorder
                   FluidEngine.beginStroke/endStroke ────────►   (app/session-recorder.js)
   Paint: clear/undo/redo/resize/bake/palette… ── command hook ─►
```

- **Тіки — на межі рушія.** Записується лише те, що реально виконав `advance()`.
  Тіки, відкинуті обмеженням у 5 кроків на виклик, у запис не потрапляють, тож
  повтор відтворює фактичний результат, а не намір.
- **Команди — на рівні `Paint`.** Undo/Redo відновлюють знімки текстур, які в
  сесію не кладуться. Повтор виконує ту саму команду застосунку, а вона бере
  знімки, створені під час повтору.
- **Story playback під час запису** записується на тих самих межах (тіки +
  `paintPathSegment`). Повтор сесії не потребує вихідного Tilecraft-файлу.

**Вимоги до продуктивності захоплення**

| ID | Вимога |
|---|---|
| PERF-REC-1 | Жодного об'єкта на тік. Тіки пишуться в блоки `Float32Array` по 4096 тіків (x, y, h). |
| PERF-REC-2 | Жодних нових слухачів pointer events і викликів `getCoalescedEvents()` для запису. |
| PERF-REC-3 | Під час мазка — лише запис у typed array. Кодування й gzip — один раз, на Stop (фаза 3: ≈ 8 Б/тік, 36 000 тіків — мілісекунди; поштучне кодування в `requestIdleCallback` не знадобилось). |
| PERF-REC-4 | Накладні витрати recorder ≤ 0,1 мс на кадр (p95) на desktop-QA пристрої; без recorder обсерватор — `null` і не коштує нічого. |
| PERF-REC-5 | Ліміт сесії — 432 000 тіків активного малювання (2 год, ≈5 МБ RAM у сирих блоках). На ліміті запис зупиняється сам із повідомленням у картці; записане зберігається. |

### 2.3. Зміни в `FluidEngine` (публічне API)

| API | Призначення |
|---|---|
| `setSessionObserver(observer \| null)` | Синхронні виклики `observer.onTick(x, y, height, scale)`, `onIdleTick()`, `onContact(x, y, pressure)`, `onBeginStroke(params, variation)`, `onEndStroke()`, `onPathSegment(args)`. Аргументи — примітиви, без алокацій. Помилка в обсервері не має ламати мазок: обсервер від'єднується, у консоль іде error. |
| `stepTick()` | Рівно один крок з поточною live-ціллю (той самий код, що тіло циклу в `advance()`, винесений у спільний `_tick()`). Потрібен для INV-MAX-1 і для повтору. |
| `replayTick(x, y, height, scale)` | Повтор: `brush.update` + контакт (якщо мазок активний) + `simulate()`. Використовує той самий `_tick()`; окремої копії логіки бути не може. |
| `beginStroke({ …, variation })` | Необов'язкова варіація натискання для повтору. Перевіряється `[0, 1)`; якщо передана, `_nextRandom()` для неї не викликається. |
| `reseedBristleRandoms(seed)` | Заповнює `randomsTexture` детермінованим PRNG (mulberry32). Зараз текстура заповнюється раз у конструкторі з `Math.random` (якщо не задано `?seed=`), тому без цього повтор після перезавантаження сторінки мав би інший jitter ворсинок. Заборонено під час активного мазка. |

### 2.4. Формат A — журнал тіків (`.flus`)

**Контейнер**

| Зсув | Поле |
|---|---|
| 0 | `"FLUS"` (4 байти) |
| 4 | `u8` formatVersion = 1 |
| 5 | `u8` flags (біт 0: є baseline PNG; біт 1: є секція C) |
| 6 | gzip-потік (`CompressionStream('gzip')`) з тілом нижче |

**Тіло**

1. `u32` довжина + header (UTF-8 JSON):
   ```json
   {
     "app": "fluid-paint", "appVersion": "…", "engineContract": 1,
     "created": "2026-10-26T13:36:11Z", "durationSec": 612.4,
     "painting": { "width": 1600, "height": 1000 }, "resolutionScale": 1,
     "paletteMode": "natural", "fluidity": 0.8, "bristleCount": 100,
     "bristleSeed": 2654435761,
     "tickEncoding": "float32-pred2",
     "baseline": "empty | png",
     "stats": { "strokes": 37, "ticks": 18342, "idleTicks": 2210 },
     "stopReason": "stop | limit | resize | background | error"
   }
   ```
   `painting` також несе `left`/`bottom`: тіки записані в координатах світу,
   повтор ставить painting rectangle туди ж (фаза 4).
2. Якщо flags.0 — `u32` довжина + PNG baseline (див. 2.6).
3. Потік записів `tag:u8` + payload:

| Tag | Запис | Payload |
|---|---|---|
| `0x01` | STROKE_BEGIN | varint len + JSON: `x, y, pressure, brushSize, color, brushShape, randomizeBristles, resolutionScale, paintingRectangle, spacing, timing, variation` |
| `0x02` | TICKS | varint `n`, далі `n` × (zigzag-varint `rx`, `ry`, `rh`) — залишки в ulp float32 |
| `0x03` | STROKE_END | — |
| `0x04` | CONTACT | `f64` x, y, pressure (LE) — рідкісні, зберігаються точно |
| `0x05` | IDLE | varint кількість холостих тіків |
| `0x06` | COMMAND | varint len + JSON (`{"op":"undo"}`, `{"op":"resize","width":…}`, `{"op":"path", …}` …) |
| `0x10` | KEYFRAMES | секція C, наприкінці файлу (2.5) |
| `0xFF` | END | — |

**Кодування тіків (рішення власника 2026-10-26, після фази 2).** Тіки — точні
float32 у координатах світу, тобто ті числа, які отримав `brush.update()`
(GPU однаково бачить лише float32). `scale` не зберігається: рушій завжди тікає з
`brushSize` мазка. Кожна компонента прогнозується як `fround(2pᵢ₋₁ − pᵢ₋₂)` (для
першого тіку мазка — точка `STROKE_BEGIN`, висота від 0; для другого — перший
тік), а записується відстань між фактичним і прогнозованим float32 в ulp
(монотонний ключ бітів float32), zigzag-varint.

Чому не кванти: фаза 2 виміряла, що динаміка хаотична — зсув тіка на ≈ 1 ulp
float32 вже дає ≈ 7 % пікселів з відхиленням > 2; `xy: 64/h: 4096` — 91 %
пікселів у ±2, жоден квант аж до 1/65536 px не дає 99 %.

**Бюджет розміру** (перевіряється `debug/session-codec-test.js` на синтетичному
корпусі; на ручному QA-корпусі — у фазі 4):

| Величина | Ціль | Виміряно (фаза 3, синтетика, 36 129 тіків) |
|---|---|---|
| Тіки до gzip | ≤ 9 Б/тік | 8,23 |
| Файл без baseline | ≤ 300 КБ на 10 хв активного малювання (36 000 тіків) | 235 КБ (6,7 Б/тік) |
| Для порівняння | поточний story JSON — 86 Б/точку, 16 Б/точку після gzip | |

**Точність.** Повтор з файлу дорівнює повтору з float32-тіків: на GPU-пробі
фази 3 — побітово (SwiftShader), у фазі 2 float32 давав ±1 через CPU-розмір
splat-області. Критерій лишається AC-REC-5.

### 2.5. Формат C — опорні точки (похідний від A)

Генерується з тіків кожного мазка (фаза 5: на Stop, разом з кодуванням A — `app/session-keyframes.js`)
і пишеться секцією `KEYFRAMES` після останнього запису, перед `END` (varint len + JSON):

```json
{ "quanta": { "xy": 64, "p": 4096 },
  "strokes": [ { "begin": 0, "t": [0, 14, 17], "x": [..], "y": [..], "p": [..] } ] }
```

- Точки мазка: точка `STROKE_BEGIN` (`t = 0`), по точці на тік (`t = 1…n`), фінальний
  `CONTACT`, якщо був (`t = n`). Тиск тіку — `height / (2 · brushSize)` (`STROKE_HEIGHT_SCALE`);
  підлогу 0,15 так не відновити, але й малює вона так само.
- Спрощення: Ramer–Douglas–Peucker у просторі `(x, y)` з `ε = 0,5` px світу;
  тиск додатково зберігає точки, де `|Δp| > 0,02` від останньої збереженої за тиском, і
  локальні екстремуми (з гістерезисом 0,005: шум float на сталому тиску — не екстремум).
  Перша й остання точки мазка зберігаються завжди.
- `t` — індекс тіку від початку мазка (час, а отже швидкість і прискорення,
  відновлюються з нього). Масиви — цілі числа, delta-кодовані (перше значення абсолютне):
  `t` у тіках, `x`, `y` у 1/64 px, `p` у 1/4096.
- `begin` — порядковий номер `STROKE_BEGIN` у потоці A (колір, пензель, варіація не дублюються).
- Ціль: приблизно у 5–10 разів менше точок, ніж тіків. Виміряно (фаза 5): ручні мишачі мазки
  QA — 11–32×; синтетика (тиск із розмахом 0,3 кожні 1,8 с) — 4,6×, без правил тиску 10,4×.
  Секція додає до файлу ≈ 47 КБ на 10 хв синтетики: 282 КБ разом, у межах AC-REC-6.

Використання C:

1. **Резервний повтор (Vector).** Якщо потік A несумісний (інший
   `engineContract`), Player пропонує повтор за опорними
   точками через replay-режим `strokeTo()`. Його результат не залежить від часу
   і від нарізки сегментів. Це наближення, і UI так і каже (2.7).
   Фаза 5: мазок — `beginStroke({ timing: 'replay' })` з точки 0, тіки мазка лише задають темп
   (на тіку `n` іде `strokeTo()` усіх точок з `t ≤ n`), решта точок і `endStroke()` — на
   `STROKE_END`. Холості паузи й команди грають як в Exact. Thickness множить `brushSize` і
   `spacing`. Пошкоджений блок сюди не входить: gzip охоплює все тіло, тож пошкоджений файл
   не декодується зовсім і Open показує помилку.
2. **Попередній перегляд** — тонкі полілінії мазків у картці Open (P5, необов'язково).
3. **Майбутнє:** експорт у Tilecraft story JSON. Поза обсягом цієї специфікації.

### 2.6. Початок запису на непорожньому полотні

Мокрий стан (float-текстури RYB) не кладеться у файл: це десятки МБ.
Тому, якщо на момент Record полотно непорожнє, записується **baseline** —
PNG видимого малюнка (той самий шлях, що `exportPngBlob()`). Під час повтору
baseline стає фоном через `setBackgroundImage()`, як після Bake. Обмеження:
фарба сесії не змішується мокрим способом з фарбою, що була до Record. Це
зазначено в картці при старті запису (2.7).

**Record починає з того стану, з якого починає повтор** (фаза 4): непорожнє
полотно запікається у фон (той самий Bake, без запису команди), порожнє —
скидає швидкість, тиск і splat-області (`engine.clear({ dynamics: true })`). Ні
мокрої фарби, ні швидкості у файлі немає, тож без цього живий запис мішав би нові
мазки з мокрою фарбою, а повтор — ні: виміряно 0,934 пікселів у ±2 замість 1.
Тиск і дивергенція поза областю симуляції теж пережили б Clear і Bake (кожен
крок чистить їх лише в області): 0,9975 у ±2, але `maxDelta` 105.

### 2.7. UI — вкладка **State**

Нова картка **Session recording** — перша у вкладці State, над Brush Angle та Bake.

```text
┌ Session recording ───────────────────────────┐
│ ● REC 02:14 · 37 strokes · ~41 KB            │  ← status, aria-live=polite, ≤1 оновлення/с
│                                              │
│ [ ■ Stop ]                                   │  ← primary; у стані Idle: [ ● Record ]
│ [ Save ]  [ Open… ]                          │
│                                              │
│ Starts from: (•) current painting as background │  ← лише коли полотно непорожнє і Idle
│              ( ) clear canvas first            │
└──────────────────────────────────────────────┘
```

**Стани та кнопки**

| Стан | Статус | Record/Stop | Save | Open… |
|---|---|---|---|---|
| Idle, нічого не записано | `Not recording` | `● Record` | disabled | enabled |
| Recording | `● REC mm:ss · N strokes · ~S KB` | `■ Stop` | disabled | disabled |
| Recorded (не збережено) | `Recorded 10:12 · 37 strokes · 41 KB — not saved` | `● Record` | enabled | enabled |
| Saved | `Saved painting-session-20261026-1336.flus` | `● Record` | enabled | enabled |

**Поведінка**

- **Record.** Генерує `bristleSeed`, викликає `engine.reseedBristleRandoms(seed)`,
  за потреби бере baseline (або очищує полотно, якщо обрано «clear canvas first»),
  під'єднує обсервер. Якщо ручний мазок триває, запис стартує з наступного
  `beginStroke` (половини мазка у записі не буває).
- **Індикатор поза панеллю.** Поки йде запис, у куті полотна видно чіп
  `● REC` (червона крапка, `role="status"`). Закриття панелі розширень **не**
  зупиняє запис, на відміну від Player, який закриття ставить на паузу. Тап по
  чіпу відкриває State tab.
- **Stop.** Завершує активний мазок у записі (той самий порядок, що й
  `yieldToManualInput`), від'єднує обсервер, добудовує C (фаза 5: одразу, разом з кодуванням A —
  ≈ 10 мс на 36 000 тіків, `requestIdleCallback` не знадобився).
- **Save.** Збирає контейнер і завантажує
  `painting-session-YYYYMMDD-HHMM.flus` тим самим механізмом, що й
  `Paint.save()` (anchor + `download`). Після Save стан `Saved`.
- **Незбережена сесія.** Record, Open… та закриття сторінки при стані
  `Recorded` спершу показують у картці inline-попередження
  `Unsaved recording will be discarded` з кнопками `Discard` / `Cancel`,
  без модального діалогу. Також ставиться `beforeunload`.
- **Open….** Приймає `.flus` (input `accept=".flus"`). Перевіряє
  magic, версію, `engineContract`, ліміт 25 МБ. Показує підсумок у картці:
  тривалість, мазки, тіки, розмір, режим повтору (`Exact` або `Vector — approximate`),
  наявність baseline, і кнопку `Open in Player →`.
- **Взаємодії.** Record вимкнений, поки Player програє `.flus`
  (запис власного повтору — рекурсія), з підказкою в `title`. Запис Tilecraft
  story playback дозволений, якщо story стартує після Record: поки story грає
  або на паузі, Record вимкнений (baseline story, взятий до запису, повтор не
  мав би). Undo/Redo/Clear/Bake/Quality під час запису дозволені й
  записуються командами. Resize і зміна фону завершують запис (2.1).
- **Undo-історія починається з Record** (фаза 3): повтор стартує з порожнього
  undo-кільця, тож Undo за межу Record не можна було б відтворити.
- **Mobile (≤ 640 px).** Картка в тій самій bottom sheet; touch targets ≥ 44 px;
  кнопки Save/Open в один ряд, Record/Stop на всю ширину.
- **Доступність.** Record/Stop — одна кнопка з `aria-pressed`; зміна стану
  оголошується через `aria-live` статусу, а не таймером щосекунди (таймер
  оновлює лише видимий текст).

### 2.8. Player для `.flus`

Відкрита сесія стає джерелом Player'а так само, як Tilecraft-файл.

| Елемент Player | Для `.flus` |
|---|---|
| Play/Pause/Resume/Restart/Stop | Як для story |
| Speed `0.25×…16×`, `Max` | `1×` = 60 тіків/с, тобто реальний темп оригіналу; `Max` — `BudgetTickScheduler` (1.3) |
| Replace / Add over current painting | Як для story; Replace також застосовує baseline |
| Progress | `ticks done / total`, підпис `12 / 37 strokes` |
| Previous/Next Frame | Disabled у v1: пропуск мазків змінює мокре змішування наступних |
| Thickness | Disabled для `Exact` (змінило б сам запис); enabled для `Vector` |
| Import colors | Прихований: сесія містить pigment-колір рушія, а не display RGB |
| Холості паузи | Серії `IDLE` скорочуються до 61 тіку (`FRAMES_TO_SIMULATE` + 1): `frameNumber` росте лише в `simulate()`, тож область, створена поза тіком (фінальний контакт, path), живе 61 крок; далі `simulate()` нічого не робить. Після останнього запису — ще 61 холостий тік: живе полотно після Stop теж осідало |
| Painting rectangle | Ставиться в `header.painting` (Replace і Add); якщо не видно цілком — вигляд зменшується зумом (не нижче 0,25), координати не зсуваються |
| Пауза | Повтор лишає годинник рушія собі: хост на паузі не робить кроків рідини (інакше додались би холості тіки, яких у записі нема). Зміна швидкості не перезапускає прогін |
| Ручний мазок під час повтору | Скасовує прогін, як у story; відкритий мазок сесії дограється одразу до `end`, Resume продовжує з наступного запису |
| Undo-історія | Повтор починає з порожнього кільця, тож прогін не відміняється одним Undo, як story |

## 3. Критерії приймання

| ID | Критерій |
|---|---|
| AC-MAX-1 | У `#story-speed` є опція `Max` останньою, під `16×`; `?storySpeed=max` її вибирає. |
| AC-MAX-2 | Для fixture `story-2026-09-08-4-frames.json` на одному пристрої `exportPixels()` після Max побітово дорівнює результату 16×. |
| AC-MAX-3 | Кожен fast-тік — рівно один крок (INV-MAX-1), включно з тіком, що триває > 16,7 мс (тест зі штучною затримкою). |
| AC-MAX-4 | На desktop-QA Max повністю програє fixture щонайменше так само швидко, як 16×, і кадр > 2·D не триває довше 1 с поспіль. |
| AC-MAX-5 | Статус показує виміряний `≈N×` і ticks/s; ETA для Max рахується з виміру. |
| AC-REC-1 | Record → кілька мазків → Stop → Save дає `.flus`, що відкривається через Open… і програється в Player. |
| AC-REC-2 | Закриття панелі під час запису не зупиняє його; видно чіп `● REC`. |
| AC-REC-3 | Ручний мазок, що почався до Record, у запис не потрапляє. Мазок, що триває під час Stop, записаний повністю до `endStroke`. |
| AC-REC-4 | Undo, Redo, Clear, Bake, Quality і зміна Natural/Digital під час запису відтворюються при повторі. Resize і зміна фону завершують запис, записане зберігається. |
| AC-REC-5 | Exact-повтор на тому ж пристрої після перезавантаження сторінки: ≥ 99 % пікселів `exportPixels()` відрізняються від оригіналу на ≤ 2 у кожному каналі. |
| AC-REC-6 | Розмір файлу на QA-корпусі: тіки ≤ 9 Б/тік до gzip, ≤ 300 КБ на 36 000 тіків без baseline. |
| AC-REC-7 | PERF-REC-1…4: накладні витрати ≤ 0,1 мс/кадр p95; жодних об'єктів на тік. |
| AC-REC-8 | Незбережена сесія не губиться мовчки: Record, Open… і закриття вкладки попереджають. |
| AC-REC-9 | Файл з іншим `engineContract` відкривається у режимі `Vector — approximate` за секцією C; без секції C — зрозуміла помилка, жодних винятків у консолі. |
| AC-REC-10 | Вкладка State на 320 px: без горизонтального overflow, targets ≥ 44 px. |
