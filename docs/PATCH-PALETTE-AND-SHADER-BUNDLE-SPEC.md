# PATCH: незалежна палітра Natural / Digital та шейдери в bundle

Дата: 2026-10-13. Статус: специфікація для реалізації; runtime-код не змінено.

## 1. Мета та межі

Два незалежні патчі для самостійного застосунку Fluid Paint:

1. Natural / Digital перемикає палітру та колір майбутніх мазків, не
   переінтерпретовує вже намальоване полотно.
2. Зібраний застосунок отримує всі потрібні `.frag` та `.vert` з `bundle.js`,
   без окремих мережевих запитів до шейдерних файлів.

Не входять: редагування окремих старих мазків, нова фізична модель змішування,
міграція на інший bundler, публікація на Netlify, зміни vendored Tilecraft
transport/model/bridge або зовнішніх репозиторіїв.

## 2. Підтверджені причини

### P1 — глобальна переінтерпретація кольорів

`paint.js` змінює `this.colorModel` з кнопок Natural / Digital та передає його
в `renderToTexture()`, `exportPixels()` і Bake. `_strokeColor()` при цьому
записує результат `hsvToRyb()` незалежно від перемикача.

`fluid-engine/shaders/painting.frag` декодує всю `paintTexture` через
пігментний куб для Natural або `1.0 - ryb.yxz` для Digital. У текстурі немає
ідентифікаторів мазків або їхніх індивідуальних моделей кольору. Зміна
рендерера тому змінює вигляд усього накопиченого матеріалу.

Додатковий шлях зміни тієї самої змінної —
`app/story-playback-controller.js::_applyColorModel()`.

### P2 — шейдери поза JavaScript bundle

`gulpfile.js::scripts()` конкатенує лише JavaScript. Завдання `engineShaders`
та `appShaders` копіюють файли у `dist/`. `common.js::loadShaderTrees()`
викликає `WrappedGL.loadTextFiles()`, який робить XHR для кожного файла.

Поточні маніфести застосунку містять 19 engine та 3 app шейдери. `304` у
Network означає перевірку кешу, а не відсутність мережевого запиту. Старі
`picker.frag` / `picker.vert` є на диску, але не потрібні поточному застосунку.

## 3. P1: контракт палітри та полотна

### 3.1 Обране рішення

Палітра визначає видимий RGB нового кольору. Полотно використовує один
постійний спосіб кодування RGB, сумісний з наявним Digital-рендерером.

Для цього патчу не потрібно міняти структуру GPU-текстури або додавати
окрему текстуру на кожен мазок:

```text
HSV + paletteMode -> displayRGB
displayRGB = [r, g, b]
storedChannels = [1 - g, 1 - r, 1 - b]
painting.frag з RGB -> displayRGB + освітлення
```

Назва `space: 'pigment'` у чинному Stroke API залишається сумісною. У цьому
застосунку її канали будуть закодованими RGB для фіксованого RGB-рендерера.
Цю домовленість потрібно явно описати біля адаптера; не передавати прямий
RGB під виглядом пігментних каналів.

Natural-кольори отримувати через чинний `hsvToPigmentRgb(..., false)`,
Digital — через `hsvToPigmentRgb(..., true)`. Зберегти чинний вигляд палітр;
цей патч не робить Digital-палітру звичайним HSV-колом.

**Прийнятий компроміс:** Natural зберігає вигляд вибраних кольорів, але
змішування перекриттів відбувається в спільному кодуванні RGB. Воно не буде
тотожним попередньому змішуванню координат пігментного куба. Збереження
старого пігментного змішування разом з повним Digital-діапазоном потребує
окремої специфікації матеріалу. Не заявляти таку сумісність у цьому патчі.

### 3.2 Стан застосунку

- Додати окремий `paletteMode: 'natural' | 'digital'`, початково `natural`.
- Рендеринг полотна завжди використовує `FluidEngine.COLOR_MODEL.RGB`.
  Не визначати цей параметр через стан кнопок або story-палітри.
- Усі зміни палітри проводити через один метод застосунку. Він синхронізує
  кнопки, picker, HEX, hue stripe, brush preview та brush center marker.
- Перемикання не змінює paint/velocity textures, фон, розмір полотна,
  snapshots або Undo/Redo; не викликає Clear, Bake чи replay.
- Зберегти наявні обмеження перемикання під час активного story playback.
- Колір мазка фіксується при його початку; зміна палітри впливає на наступний
  мазок, а не на продовження вже активного.

### 3.3 Внесення кольору

Створити спільний адаптер видимого RGB у канали текстури. Використати його
для ручного малювання, story playback та зовнішнього API кольору.

`_strokeColor()`:

1. Обчислює видимий RGB відповідно до `paletteMode`.
2. Для ad-hoc White / Black використовує точні `[1,1,1]` / `[0,0,0]`.
3. Кодує RGB як `[1-g,1-r,1-b]`.
4. Залишає чинну криву alpha, pressure, bristle count та форму мазка.

Не переносити освітлення, diffuse/specular або висоту в колір внесення.
Кодується базовий RGB матеріалу; освітлення залишається в рендерері.

Колір з HEX у story або control API — це вже запитаний видимий колір.
Не пропускати його повторно через Natural-куб: кодувати безпосередньо для
постійного RGB-полотна. Не застосовувати стару Natural inverse-конверсію
лише тому, що Natural зараз вибраний у UI.

`StoryPlaybackController.colorModel` та чинні значення story UI можуть
залишитися для сумісності, але в цьому застосунку вони означають вибір
палітри. При побудові payload для engine слід окремо задавати постійне
кодування полотна. Не міняти глобально стандартну поведінку
`TilecraftStrokePlayer.hexToPigment()` для інших хостів.

Якщо HEX переводиться в HSVA для UI, конверсія має відновлювати колір у
поточній палітрі. За неможливості точного відтворення зберігати точний RGB
як явний override до наступної ручної зміни H/S/V; HEX, preview і внесення
мають показувати та використовувати однаковий колір.

### 3.4 Рендеринг, історія та сумісність

- Screen render, resize preview, PNG export і Bake використовують однакову
  постійну RGB-модель.
- PNG-фон залишається окремим сухим шаром. Перемикання палітри не змінює його.
- Undo/Redo відновлює матеріал у тому самому форматі, без конверсії текстури.
- Зберегти API й стандартну RYB-поведінку FluidEngine для інших хостів та
  `examples/minimal`; нова політика стосується застосунку Fluid Paint.
- Старі пігментні snapshots не можна мовчки трактувати як новий RGB-формат.
  Якщо знайдеться шлях відновлення таких даних між сесіями, його потрібно
  версіонувати або явно мігрувати. Звичайний PNG не потребує міграції.

### 3.5 Файли реалізації

Основні: `paint.js`, `app/ui/color.js`, `app/ui/ryb.js`,
`app/story-playback-controller.js`, `app/fluid-control-api.js`.
Перевірити всі споживачі `colorModel`, включно з debug-тестами та адаптером
`fluid-engine/tilecraft-stroke-player.js`. Не міняти фізику симуляції.

Оновити `docs/COLOR-PICKER-PAINT-PARITY-SPEC.md` та позначити старий опис
Natural/Digital у `docs/PAINT-STATE-AND-EDITING-SPEC.md` як поведінку до патчу.

## 4. P2: шейдери в bundle

### 4.1 Build

Додати в Gulp генерацію JS-реєстру текстів шейдерів перед конкатенацією.
Використати engine/app маніфести як джерело набору потрібних файлів;
не підтримувати третій незалежний список вручну.

- Ключ реєстру — повний шлях джерела, наприклад
  `fluid-engine/shaders/painting.frag` або `app/shaders/shadow.frag`.
  Це запобігає колізіям між деревами.
- При передачі в engine зберігати чинні логічні ключі `shaders/painting.frag`.
- Реєстр має бути доступний до запуску `loadShaderTrees()`.
- Серіалізувати тексти як JS-рядки без GLSL-мініфікації: зберегти newline,
  директиви preprocessor і порядок `#define` / GLSL3-конверсії.
- Відсутній, порожній файл або колізія ключів зупиняє build з повідомленням
  про конкретний шлях. Build не повинен завершитися успішно з неповним набором.
- Генерований файл зберігати у build/temp-каталозі; не комітити й не редагувати
  вручну. Порядок Gulp tasks має виключати гонку генерації та `scripts()`.
- Зміна шейдера або маніфесту в dev перебудовує реєстр і bundle.

### 4.2 Runtime та source mode

`loadShaderTrees()` отримує джерела з реєстру, якщо той присутній.
У bundled mode відсутній запис — явна помилка ініціалізації; не робити
прихований XHR fallback, який маскує зламану збірку.

Коли реєстру немає, зберегти файловий loader для source mode та прикладів.
Перевіряти HTTP-успіх і мережеві помилки перед передачею тексту компілятору;
HTML сторінки 404 не повинен ставати текстом шейдера. Completion callback
викликати рівно один раз, включно з порожнім набором; помилку доставляти
через узгоджений error callback або Promise до UI ініціалізації.

Engine залишається незалежним від I/O: як і раніше, хост передає готовий
`shaderSources` у конструктор. Не додавати залежність engine від app-реєстру.

Окремі шейдерні файли можна залишити в `dist/` для сумісності. Критерій патчу
— зібраний застосунок їх не запитує й запускається без доступу до них.

Основні файли: `gulpfile.js`, `common.js`, за потреби
`fluid-engine/gl/wrappedgl.js` та спільний manifest/build helper.
Оновити `DEPLOY.md` і `docs/SDLC.md` відповідно до фактичної збірки.

## 5. Приймання та перевірки

### P1

1. Намалювати кольори в Natural, зафіксувати engine export pixels. Без кроків
   симуляції перемкнути Digital, потім Natural: pixels мають бути ідентичні.
   Не порівнювати весь UI canvas, де змінюються прев'ю та debug overlays.
2. Повторити для малюнка, розпочатого в Digital, та змішаного набору мазків.
3. При активній симуляції порівняти два детерміновані запуски з однаковими
   кроками: перемикання палітри без нових мазків не змінює матеріал.
4. Нові мазки в обох палітрах відповідають HEX і preview за однакових умов
   освітлення. На GPU застосувати обґрунтований допуск для float/half-float;
   не вимагати рівності освітленого пікселя HEX матеріалу.
5. Перевірити White / Black, alpha, перекриття, resize, Undo/Redo, PNG-фон,
   експорт і Bake. Перемикання саме по собі не змінює Undo/Redo.
6. Перевірити точність story HEX та control API, restart і replay, а також
   збереження чинних обмежень story-перемикача.

Додати GPU-регресію незмінності полотна та перевірки кольорового адаптера.
Чинний `test:color` зараз проходить 42/42, але не перевіряє цей дефект.
Оновлювати його лише там, де контракт справді змінився.

### P2

1. `npm run build` створює повний реєстр шейдерів у `bundle.js`.
2. Браузерний тест відкриває `dist/` і блокує всі `.frag` / `.vert` запити:
   застосунок ініціалізується та малює; кількість таких запитів дорівнює нулю.
3. Перевірити WebGL1 та WebGL2, включно з варіантами screen/resize/save.
4. Source mode та `examples/minimal` працюють з файловим завантаженням.
5. Відсутній файл ламає build; неповний runtime-реєстр та source HTTP-помилка
   дають зрозумілу помилку замість зависання або компіляції HTML.
6. У dev зміна тексту шейдера потрапляє в наступний bundle.

Перед завершенням виконати релевантні color, shader lint, story, control API,
Bake та GPU-тести, потім обов'язкову перевірку репозиторію за `docs/SDLC.md`.
Зафіксувати результати та обмеження фізичної GPU-перевірки.

## 6. Порядок реалізації та готовність

P1 і P2 реалізувати окремими змінами, кожну з власними перевірками. Для P1
спочатку адаптер кольору та GPU-регресія, потім усі entry points і UI. Для P2
спочатку генерація та loader, потім watch, браузерна регресія й документація.

Патч готовий, коли обидві групи критеріїв виконані, build відтворюваний,
сумісність інших engine-хостів перевірена, а зміна Natural-змішування явно
описана. Deploy не є частиною виконання цієї специфікації.
