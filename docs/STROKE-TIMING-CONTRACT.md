# Stroke timing contract — Phase 9a, revised

Стан на 2026-09-08. Гілка `fluid-engine-v2`, поверх `4125bc0` («pahse 9a non
complete»). Цей документ **виправляє** §"Scope and API level", §"Exact step
order" і §"Phase 9a verification" у `docs/HANDOFF2.md`; там, де вони
суперечать цьому файлу, чинним є цей.

> **Далі:** реалізація за цим контрактом, потім `QA.md` і golden.

## Чому спека була неправильна

HANDOFF2 задавав:

> Each method performs all brush, splat, and fluid steps needed for its portion
> of the stroke before it returns.

> While named-stroke state is active, direct calls to … `frame()` … must throw
> `StrokeStateError`.

> changing caller timing, including long pauses, does not change output

Разом це **ототожнює просторовий крок із кроком фізичного часу**. Реалізація
`4125bc0` виконала це буквально: `_strokeSample()` робить
`brush.update → splat → simulate()` на кожну точку просторового
пересемплювання, а `Simulator.simulate()` просуває фіксований
`DELTA_TIME = 1/60` с ([simulation.js:739](../fluid-engine/simulation.js#L739)).

Виміряні наслідки (підставна симуляція, пензель 50, spacing 7.5):

| сценарій | що стається |
|---|---|
| рух 300 px одним викликом | 40 кроків ≈ **0.67 с фізики** за один callback |
| `beginStroke()` | ще 10 кроків синхронно, до першого показу |
| натиснуто, курсор стоїть | `strokeTo` без руху → 0 кроків → **фарба завмирає** |
| рух 3 px (< spacing) | 0 кроків; ще й геометрія пензля не оновлюється |
| швидкий довгий рух | обсяг GPU-роботи за callback **не обмежений** |

Останнє не косметичне: кожна проміжна точка — це оновлення щетинок із 20
ітераціями обмежень плюс повний крок рідини.

**Хибна вимога:** однаковий результат для однакової геометрії шляху незалежно
від часу вводу. Для рідкої фарби швидкість руху й тривалість паузи — частина
фізичного вводу; той самий шлях за 100 мс і за 2 с не зобов'язаний давати
однакову картину.

**Правильна детермінованість:** однаковий результат для однакової послідовності
**(позиція, тиск, час)** за однакового початкового стану.

## Чотири окремі речі

Реалізація `4125bc0` злила їх в одну. Контракт їх розділяє:

| # | що | хто володіє | одиниця |
|---|---|---|---|
| 1 | приймання вводу | хост → движок, дешево | подія (x, y, тиск, **timestamp**) |
| 2 | просторове пересемплювання **відбитків** | движок | px уздовж шляху |
| 3 | просування фізичного часу | движок, за годинником | с, кроками по `DELTA_TIME` |
| 4 | рендер | хост | кадр |

Ключове: **(2) і (3) незалежні.** Відбиток — це де мазок торкнувся паперу.
Крок часу — це скільки фізики минуло. Одне не породжує інше.

## Часовий контракт

### C1. Час просувається за годинником, не за RAF і не за відстанню

RAF — не фізичний годинник: один крок 1/60 на кожен RAF дає різну швидкість
фізики на 30, 60 і 144 Hz. Движок веде акумулятор:

```
accumulator += clamp(now - lastNow, 0, MAX_FRAME_TIME)
steps = 0
while accumulator >= DELTA_TIME and steps < MAX_STEPS_PER_FRAME:
    runStampsDueIn(simTime, simTime + DELTA_TIME)   // C5a
    simulate()                                      // один крок DELTA_TIME
    simTime += DELTA_TIME
    accumulator -= DELTA_TIME
    steps++

// Відкинути ВСІ залишкові повні кроки; лишити тільки дробовий залишок.
// fmod, а не min(acc, DELTA_TIME): min лишає один цілий крок на майбутнє,
// тобто борг переноситься, що суперечить C2a.
dropped = 0
if accumulator >= DELTA_TIME:
    dropped = floor(accumulator / DELTA_TIME) * DELTA_TIME
    accumulator -= dropped                          // 0 <= accumulator < DELTA_TIME
    simTime += dropped                              // C2b: годинник не відстає
droppedSeconds += dropped
```

Після кадру завжди `accumulator < DELTA_TIME`.

- `DELTA_TIME = 1/60` — **не змінюється**: це вже одиниця часу движка, і
  `FRAMES_TO_SIMULATE = 60` рахує саме кроки, а не секунди
  ([simulation.js:4](../fluid-engine/simulation.js#L4)).
- `MAX_FRAME_TIME = 0.25 c` — стеля на один кадр.
- `MAX_STEPS_PER_FRAME = 5` — стеля роботи за кадр.

### C2. Політика для довгих зависань і прихованої вкладки

Явно, бо мовчазна поведінка тут — це або стрибок фізики, або накопичений борг:

- проміжок > `MAX_FRAME_TIME` **обрізається** до нього (не наздоганяємо годинами);
- `visibilitychange` на `hidden` → зупинити акумулятор; на `visible` → скинути
  `lastNow` у `now` і **не** нараховувати проміжок за час у фоні.

#### C2a. Що стається з невиконаним боргом

Однозначно: **борг відкидається, не переноситься.**

Приклад, який це задає. Пауза 250 мс дає `accumulator = 0.25 с` = 15 кроків
рівно. Виконуються `MAX_STEPS_PER_FRAME = 5` (`accumulator` → 10/60 с). Решта
**10 кроків не виконуються ніколи**: `accumulator` зменшується на
`floor(10/60 / DELTA_TIME) × DELTA_TIME = 10/60`, тобто до **0**, і
`droppedSeconds += 10/60`.

Саме `floor`-відкидання, а не `min(accumulator, DELTA_TIME)`: останнє лишило б
один цілий крок на наступний кадр — тобто 5 виконано, 9 відкинуто, 1
перенесено. Це вже перенесення боргу, хай і на один крок, і воно суперечить
цьому ж пункту.

Чому відкидати, а не переносити: перенесення означає, що після кожного
підгальмовування движок ще кілька кадрів працює на стелі бюджету, наздоганяючи
минуле. Це розтягує один лаг у серію лагів і робить час кадру залежним від
історії. Відкидання дає інший, але **обмежений** ефект: під перевантаженням
симуляційний час іде повільніше за реальний.

Наслідок, який треба назвати прямо, бо він обмежує A4: **незалежність від
частоти кадрів гарантується лише в режимі без перевантаження** — коли
`elapsed ≤ MAX_STEPS_PER_FRAME × DELTA_TIME` (≈ 83 мс). Щойно час відкидається,
очікується **визначена деградація**, а не ідентичний результат: менше
симуляційного часу за той самий реальний. Перевіряється це як властивість
(скільки часу відкинуто), а не як рівність картин.

Движок повідомляє це, а не ховає: `advance()` повертає
`{ steps, droppedSeconds, stamps, mergedPoints, queueLength, queueAgeSeconds }`,
і `droppedSeconds > 0` — вимірюваний сигнал перевантаження, на якому будується
A5 і B3.

#### C2b. Відкинутий час просуває годинник, інакше ввід відстає назавжди

Відкидання часу створює другу шкалу. Черга порівнює мітки подій із `simTime`,
а `simTime` просувається лише **виконаними** кроками — отже після кожного
відкидання `simTime` відстає від настінного годинника на відкинуте, назавжди
і накопичувально. Нові події чекали б, поки симуляція дожене їхні мітки, і
затримка зростала б із кожним перевантаженням.

Правило: **відкинутий час просуває `simTime` разом з акумулятором**
(`simTime += dropped` у C1). Інваріант, який це дає:

```
simTime  ≈  wallClockAtStrokeStart + (реальний час від початку мазка)
```

з точністю до `MAX_FRAME_TIME` і часу у фоні (C2). Тобто `simTime` — це
**часова межа обробленого вводу**, а не сума виконаної фізики. Дві величини
розрізняються явно:

| величина | що це | зростає від |
|---|---|---|
| `simTime` | доки ввід оброблено | виконаних кроків **і** відкинутого часу |
| `simulatedSeconds` | скільки фізики справді пораховано | лише виконаних кроків |

`simulatedSeconds = simTime − simTimeAtStart − droppedSeconds` — це і є
«визначена деградація» з A4b, у секундах.

**Події у пропущеному інтервалі не втрачаються.** Відбитки з мітками всередині
відкинутого проміжку наносяться в найближчому виконаному кроці, у порядку
міток, одним пакетом (їхня фізика не була пораховані — це і є деградація).
Втрачений час не означає втрачений ввід: мазок дійде до останньої позиції
пальця, просто фарба в цьому проміжку не встигне розтектися.

### C3. Нерухоме натискання просуває час і наносить фарбу

Поки мазок активний і курсор стоїть, фізика йде за C1, а щетинки далі
осідають. Це те, як `fluidity` взагалі себе проявляє. Нанесення при
нерухомому натисканні визначено в T2.

### C4. `frame()` не заборонено під час мазка

Заборона з HANDOFF2 знімається. Просування часу лишається за хостом і його RAF
— саме тому хост може малювати на 144 Hz і не отримати вчетверо швидшу фарбу.
Движок надає `advance(nowSeconds)`, що реалізує C1; `frame()` лишається
низькорівневим одним кроком.

Що **лишається** забороненим під час активного мазка: `setBrush`,
`changeResolution`, `resizePainting`, `clear`, `restoreSnapshot` — усе, що
змінює геометрію чи масштаб, які мазок уже зафіксував.

### C5. Приймання вводу дешеве; обробка — з бюджетом

`strokeTo()` **не** виконує довільну кількість splat-ів синхронно. Він ставить
подію `(x, y, тиск, t)` у чергу й повертається. Уся робота — в `advance()`.

- за кадр обробляється не більше `MAX_STAMPS_PER_FRAME` відбитків;
- при відставанні черга **не** відкидається мовчки: залишок переходить у
  наступний кадр;
- при переповненні черги діє C5b.

### C5a. Порядок: ввід і фізика чергуються вздовж часу симуляції

**Не можна** спочатку нанести всі накопичені відбитки, а потім виконати всі
кроки фізики. Це знову зробило б результат залежним від того, як події
згрупувалися в кадри — та сама помилка, що й прив'язка часу до відстані, лише
з іншого боку.

`advance()` відтворює ввід **послідовно вздовж симуляційного часу**:

```
runStampsDueIn(from, to):
    // Наносить відбитки з мітками у [from, to). Може ПЕРЕРВАТИСЯ всередині
    // сегмента: пересемплювання йде по одному відбитку, а не сегментами.
    while queue not empty and queue.head.t < to:
        if stamps >= MAX_STAMPS_PER_FRAME:
            return BUDGET_EXHAUSTED
        emitOneStamp()          // один відбиток; залишок сегмента лишається
        stamps++                // в черзі з власною міткою (C5c)
    return DONE
```

Бюджет вичерпано — **крок не виконується**. Інакше відбитки, що лишилися в
цьому кроці, потраплять у вже пізніший стан фізики наступного кадру, і порядок,
заради якого весь C5a існує, зламається саме під навантаженням:

```
while accumulator >= DELTA_TIME and steps < MAX_STEPS_PER_FRAME:
    if runStampsDueIn(simTime, simTime + DELTA_TIME) == BUDGET_EXHAUSTED:
        break                  // крок НЕ виконано; його час лишається
                               // в accumulator і дочекається наступного кадру
    simulate()
    simTime += DELTA_TIME
    accumulator -= DELTA_TIME
    steps++
```

Незавершений крок переноситься цілим: його час лишається в акумуляторі, а
недонесені відбитки — у черзі з власними мітками. Наступного кадру він
починається спочатку, з тієї ж часової межі, тому ввід і фізика лишаються
впорядкованими.

Ця гілка не оминає C2a: якщо перерви повторюються, акумулятор дійде до
`MAX_FRAME_TIME` і зайвий час буде відкинуто за тим самим правилом. Тобто
затримка обмежена, а не накопичується мовчки.

### C5b. Злиття черги при перевантаженні

«Зливаються геометрично» — недостатньо: це не гарантує ні траєкторії, ні тиску,
ні швидкості. Тому злиття визначене як **вимірюваний режим перевантаження** з
інваріантами:

Спершу — чого злиття **не** робить, бо попередня редакція це переоцінювала:

- збереження *сумарного* інтервалу часу **не зберігає локальну швидкість**:
  дві точки, злиті в одну, ховають те, що між ними рух був різкий;
- збереження *кінцевого* тиску **не зберігає профіль тиску** всередині
  злитого проміжку;
- видалення вершини ламаної **вкорочує** шлях (нерівність трикутника), тому
  «зберігається довжина шляху» не випливає з простого викидання точок.

Тому злиття визначене як **втратний режим із названими інваріантами й
виміряною похибкою**, а не як еквівалентне перетворення.

Зливаються лише **проміжні** точки одного сегмента руху. Зберігаються завжди:

- **кінцева точка** — позиція, тиск і мітка часу останньої події;
- **`beginStroke` / `endStroke`** — ніколи не зливаються й не переставляються;
- **монотонність міток** — порядок подій не змінюється.

Похибка обмежена й вимірювана:

- **геометрія:** відхилення злитої точки від вихідної ламаної
  ≤ `MERGE_TOLERANCE = 0.5 × spacing` (Дуглас-Пекер по коридору);
- **довжина шляху:** зберігається не геометрично, а **явним полем**
  `arcLength`, яке несе кожен сегмент черги. Злиття підсумовує `arcLength`
  злитих ланок, тож кількість відбитків (T1) не змінюється, навіть коли
  хорда коротша за ламану;
- **швидкість:** кожна ланка несе власний `arcLength / Δt`. Злиття зберігає
  **зважене за часом середнє** й окремо `maxSpeed` злитого проміжку, який і
  йде в T3. Пік не губиться — він стає піком ланки;
- **тиск:** зберігаються `pressureIn` і `pressureOut` ланки; всередині
  інтерполюється лінійно. Профіль спрощується — це і є втрата, названа явно.

### C5c. Пересемплювання переривається всередині сегмента

`emitOneStamp()` наносить **один** відбиток і зберігає стан пересемплювання
(пройдена вздовж сегмента відстань, залишок `remainder`). Довгий сегмент, що
дає 200 відбитків, не є неподільною одиницею: він віддає стільки, скільки
дозволяє бюджет, і лишає решту на наступний кадр.

Мітка часу відбитка — **інтерпольована за довжиною дуги** між мітками кінців
сегмента, а не мітка кінця. Тому перерваний сегмент продовжується з правильного
моменту часу, а не «стрибає» вперед.

Відбиток із міткою всередині кроку наноситься **перед** фізикою цього кроку —
той самий порядок `splat → frame`, що й у застосунку до 9a, лише тепер прив'язаний
до часу події, а не до порядку виклику.

Наслідок: два однакові набори подій із однаковими мітками дають однаковий
результат незалежно від того, чи прийшли вони одним callback-ом, чи двадцятьма
(перевірка C1 у критеріях).

### C5d. Черга обмежена; ріст черги — окрема метрика

«Інакше черга росте» з попередньої редакції лишало необмеженими і пам'ять, і
затримку, а `droppedSeconds` цього не бачить: черга може рости **без** втрати
часу.

Тому:

- `MAX_QUEUE_POINTS` — жорстка стеля довжини черги. При досягненні злиття
  виконується **навіть якщо** воно виходить за `MERGE_TOLERANCE`; тоді
  зростає `mergeErrorPx` (максимальне фактичне відхилення), і це друга
  метрика деградації поряд із `droppedSeconds`;
- `MAX_QUEUE_AGE` — стеля віку найдавнішої необробленої події. Перевищення
  означає, що бюджет відбитків не встигає за вводом: черга стискається злиттям
  до `MAX_QUEUE_POINTS / 2`.

`advance()` повертає `queueLength`, `queueAgeSeconds`, `mergedPoints` і
`mergeErrorPx`. Перевірки B3 і C5 вимірюють саме їх — час кадру сам по собі не
показує, що затримка вводу росте.

### C6. Три різні речі, які попередня редакція називала «оновленням пензля»

Попередня редакція вимагала «оновлювати геометрію щокадру». Це було
недодумано: `Brush.update()` — **не** переставляння курсора, а крок фізики.
Він інтегрує гравітацію й демпфування (`u_gravity`, `u_damping`) і проганяє
`ITERATIONS = 20` PBD-обмежень
([brush.js](../fluid-engine/brush.js)) — **без жодного параметра часу**: крок
жорстко дорівнює «один виклик». Викликати його на кожен RAF означало б
прив'язати фізику щетинок до частоти кадрів; на кожен відбиток — до spacing.
Та сама помилка, від якої написаний увесь цей документ.

Гірше, швидкість щетинок у ньому — це `sqrt(dx²+dy²+dz²)`, тобто **відстань за
виклик**, не за секунду. Вона йде не лише у вигляд: `getFilteredSpeed()`
множиться на `SPEED_PADDING` і розширює область симуляції splat-у
([simulation.js:574](../fluid-engine/simulation.js#L574)) — тобто визначає
**вартість кадру**.

Тому розділяємо три речі, які досі були одним викликом:

| # | що | коли | одиниця |
|---|---|---|---|
| C6a | **позиція вводу** пензля | щокадру, перед рендером | px, миттєво |
| C6b | **фізичний крок щетинок** | один на крок `DELTA_TIME` | `DELTA_TIME` |
| C6c | **відображення** | щокадру | — |

#### C6a. Позиція — щокадру, і вона не є фізикою

Актуальна позиція вводу записується перед показом кадру **завжди**, навіть коли
рух менший за spacing і жодного відбитка не емітовано. Це те, що
`_syncBrushToPointer()` і фікс Phase 6 забезпечували до `4125bc0`. Сама по собі
вона не інтегрує нічого — це вхідна величина для C6b.

#### C6b. Фізика щетинок іде з тим самим тактом, що й рідина

Рівно **один** крок щетинок на кожен виконаний крок `DELTA_TIME` у C1 — у тому
самому циклі, перед `simulate()`. Не на RAF і не на відбиток.

Наслідок для щетинок при нерухомому контакті: вони далі осідають (C3), бо
кроки йдуть за годинником, а не за рухом.

Переміщення, яке крок щетинок бачить, — це переміщення **за цей крок часу**, а
не за виклик: `Δ = позиція(simTime + DELTA_TIME) − позиція(simTime)`,
інтерпольована по черзі вводу. Тому:

- швидкість щетинок стає **px за секунду** (`Δ / DELTA_TIME`), а не px за
  виклик, і перестає залежати від частоти кадрів;
- `getFilteredSpeed()` та `SPEED_PADDING` починають означати те, що написано в
  їхніх назвах, а область симуляції splat-у перестає роздуватися лише тому, що
  кадр був довгий.

`Brush.update()` отримує явний `dt`. Поки він дорівнює `DELTA_TIME`, поведінка
збігається з теперішньою (крок = один виклик) — це і є орієнтир сумісності.

#### C6c. Відображення не чекає на фізику

Рендер малює останній порахований стан щетинок із C6b плюс позицію з C6a.
Кадр, у якому не виконано жодного кроку (`accumulator < DELTA_TIME`), усе одно
показує пензель у актуальній позиції — інакше повернулося б відставання, яке
B1 вимірює.

## Нанесення фарби

Просторове пересемплювання лишається зміною поведінки навіть без просування
часу: воно змінює кількість фарби на одиницю шляху. Тому визначаємо явно.

### T1. Під час руху

Відбиток кожні `spacing` px уздовж шляху, `spacing = max(1, 0.15 × brushSize)`
у **тому самому просторі, що й координати** (див. T4). Кількість фарби на
одиницю шляху стає незалежною від частоти подій — це і є мета.

Проти старої поведінки (відбиток на кадр) це змінює картину: виміряно +34%
нанесеної alpha на dpr1 у сценарії `basic`. Зміна **навмисна**, але має бути
прийнята оком, а не хешем.

### T2. При нерухомому натисканні — нанесення триває, за часом симуляції

Попередня (до `4125bc0`) реалізація наносила фарбу щокадру, поки кнопка
натиснута: RAF-цикл викликав `positionBrush → splat → frame` незалежно від
того, рухався курсор чи ні. **Це зберігається.** Зупиняти нанесення було б ще
однією зміною поведінки, якої це виправлення не потребує.

Прив'язка — до **симуляційного часу**, не до кадрів і не до відстані: один
відбиток на кожен крок `DELTA_TIME`, у якому контакт активний і рух менший за
`spacing`. На 60 Hz без перевантаження це рівно один відбиток на кадр, тобто
початковий орієнтир — попередня поведінка.

Насичення чи виснаження запасу фарби **не додаємо**: це окрема функція, не
частина цього виправлення.

### T3. Одиниці швидкості щетинок

Дві різні швидкості, які раніше були одним числом:

| що | звідки | куди йде |
|---|---|---|
| швидкість **щетинок** | C6b: `Δпозиція за крок / DELTA_TIME` | `getFilteredSpeed()` → `SPEED_PADDING` → область симуляції splat-у, тобто **вартість кадру** |
| швидкість **мазка** для імпульсу | `arcLength / Δt` ланки черги (C5b), пік — `maxSpeed` | `velocityScale` у `splat()` |

Обидві — **px за секунду**, обидві обрізані згори `MAX_STROKE_SPEED`. Обрізання
не косметичне: без нього різкий стрибок вводу роздуває область симуляції splat-у
([simulation.js:574](../fluid-engine/simulation.js#L574)) і разом із нею час
кадру.

Чому це взагалі треба було називати: відбитки емітуються за **відстанню**, тому
дельта між сусідніми відбитками стала (= `spacing`) і сама по собі більше не
несе швидкості жесту. Брати швидкість із нумерації відбитків означало б, що
швидкий і повільний мазок передають рідині однаковий імпульс — видно як
зникнення бризок на різкому русі.

### T4. Простір координат

`spacing` задається в тому ж просторі, що `x`/`y`. Хост, у якого координати —
device pixels, а `brushSize` — CSS-міра (головний застосунок при
`devicePixelRatio > 1`), **зобов'язаний** передати власний `spacing`. Інакше
той самий жест дає різну кількість відбитків на різних екранах — виміряно
**+247% нанесеної alpha на dpr2** до появи цієї опції.

## Критерії приймання

Golden сюди **не** входить: він перевіряє відповідність еталону, а не
правильність часової моделі. Golden запускається **після** цих перевірок і
разом із ними.

### A. Часова модель

| # | перевірка | критерій |
|---|---|---|
| A1 | нерухоме натискання 2 с | кроків симуляції = 2 с / `DELTA_TIME` ± 1; сумарна alpha зростає монотонно (T2 наносить) |
| A1b | те саме, але **нанесення вимкнено після t=0.5 с** (відбитки припинено, час іде) | сумарна alpha **стала**, а текстура далі **змінюється** — доводить рух уже нанесеної фарби окремо від додавання нової. Без цього A1 не відрізняє розтікання від нанесення |
| A2 | той самий шлях за 100 мс і за 2 с | картини **різні** (це фізика, не баг); обидві стабільні при повторі |
| A3 | та сама послідовність (позиція, тиск, **час**) двічі | результат ідентичний |
| A4 | той самий ввід при 30 / 60 / 144 Hz, **без перевантаження** | `droppedSeconds == 0` на всіх трьох; кроків симуляції ± 2; картини в межах допуску T1 |
| A4b | те саме **з перевантаженням** (штучний бюджет) | НЕ вимагаємо рівності: `droppedSeconds > 0`, і симуляційний час менший за реальний рівно на нього (± 1 крок) — визначена деградація, не збіг |
| A5 | зависання 3 с (штучне) | ≤ `MAX_STEPS_PER_FRAME` кроків у наступному кадрі; **у кадрі після нього теж ≤ стелі** (борг відкинуто за C2a, не переноситься); `droppedSeconds ≈ 3 − 5×DELTA_TIME` |
| A6 | вкладка прихована 10 с | після повернення 0 «наздоганяючих» кроків; `droppedSeconds` не зростає за час у фоні |
| A7 | пауза 250 мс (приклад із C2a) | виконано рівно 5 кроків, `droppedSeconds ≈ 10/60`, акумулятор після кадру ≤ `DELTA_TIME` |

### B. Відгук і вартість

| # | перевірка | критерій |
|---|---|---|
| B1 | затримка курсор → пензель | ≤ 1 кадр на будь-якому русі, **зокрема < spacing** |
| B2 | рух 3 px (< spacing), **контакт активний** | позиція пензля оновлена (C6a) і крок щетинок виконано (C6b); **просторових** відбитків 0. Часові відбитки T2 при цьому дозволені — критерій рахує саме просторові, інакше він суперечив би T2 |
| B3 | швидкий рух 800 px за один callback | час кадру ≤ 2× медіани спокійного; черга розбирається за визначену кількість кадрів; `mergedPoints` і `droppedSeconds` **виміряні**, а не припущені |
| B4 | час кадру, великий canvas | 95-й процентиль ≤ **бюджету, записаного в цей документ ДО вимірювання** (див. нижче). Бюджет, обраний після прогону, підганяється під результат і нічого не перевіряє |
| B5 | `strokeTo()` сам по собі | вартість не залежить від довжини сегмента (приймання дешеве, C5): час 20 викликів по 5 px ≈ час 20 викликів по 500 px |

### C. Нанесення

| # | перевірка | критерій |
|---|---|---|
| C1 | той самий шлях, 1 сегмент проти 23, **з тими самими мітками часу** | однакові позиції відбитків І однакове чергування з кроками фізики (C5a): той самий результат, а не лише ті самі точки |
| C1b | ті самі події, згруповані в 1 кадр проти 5 кадрів | результат ідентичний **за умов застосовності**: `droppedSeconds == 0`, `mergedPoints == 0`, і кожна подія надійшла **до** обробки кроку, у який падає її мітка. Ввід, доставлений після того, як його час уже пройшов, не можна врахувати заднім числом без replay — такий випадок перевіряється як C1c, а не як рівність |
| C1c | подія, доставлена із запізненням (мітка вже в минулому) | наноситься в найближчому виконаному кроці, у порядку міток (C2b); мазок доходить до останньої позиції; розбіжність із вчасною доставкою обмежена й **виміряна**, а не нульова |
| C2 | крайні `fluidity` (мін, макс) | фізика йде за A1 на обох; без вибуху й без застою |
| C3 | dpr1 проти dpr2, той самий жест | кількість відбитків збігається ± 2 (T4) |
| C4 | повільний рух проти швидкого | переданий рідині імпульс різний (T3) |
| C5 | перевантаження черги (штучний `MAX_QUEUE`) | кінцева точка, тиск і мітка часу збережені; `beginStroke`/`endStroke` не злиті; довжина шляху й сумарний час збережені; відхилення злитої точки ≤ `MERGE_TOLERANCE` |

### D. Регресії, які вже коштували

| # | перевірка | критерій |
|---|---|---|
| D1 | 8 тапів одним пензлем | ≥ 6 різних розкладок щетинок (Phase 8a) |
| D2 | один прес | рівно один розіграш random; жодного за рух чи відпускання |

## Бюджет часу кадру — зафіксований до вимірювання

Записано **до** прогону, щоб B4 не можна було підігнати під результат. Числа —
робочі припущення, як `MAX_STEPS_PER_FRAME`; якщо вимір їх не витримає, це
результат, який треба назвати й пояснити, а не мовчки переписати бюджет.

| величина | бюджет |
|---|---|
| час кадру, 95-й процентиль, canvas 2048×2048, quality Medium | ≤ 16.7 мс |
| час кадру, максимум, той самий canvas | ≤ 33 мс (один пропущений кадр, не серія) |
| `advance()` при спокійному мазку | ≤ 8 мс |
| `strokeTo()` сам по собі (B5) | ≤ 0.1 мс на виклик, незалежно від довжини сегмента |
| затримка курсор → пензель (B1) | ≤ 1 кадр |
| `queueAgeSeconds` при звичайному малюванні | ≤ 2 × `DELTA_TIME` |

Зміна цих чисел після вимірювання дозволена лише разом із записаною причиною в
`HANDOFF.md` — інакше критерій перестає бути критерієм.

## Що вимірювати, а не дивитися

Затримку (B1) і час кадру (B3, B4) — числами, з міток часу, а не з фінального
скриншота. Фінальний скриншот не показує ні завмирання фарби під час
натискання, ні відставання пензля.
